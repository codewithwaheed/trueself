Implementation approaches

Three ways to wire up the kill-process capability

A

Extend PreflightCheck + single kill command (Recommended)

Add an optional flagged_processes field to the existing PreflightCheck struct. Add one new Tauri command kill_process(pid, force). Frontend reads the processes out of the preflight result and renders the expanded row. Clean — no new API surface beyond one command.

Pros

  • Minimal changes to existing structs
  • All data flows through the existing preflight invoke
  • One command handles both graceful + force

Cons

  • PreflightCheck becomes slightly polymorphic
B

Separate get_flagged_processes command

Keep run_preflight unchanged (returns text only). Add a separate get_flagged_processes() command the frontend calls independently when the scan fails. Frontend fetches process list, renders the UI, calls kill_process().

Pros

  • No changes to existing PreflightCheck type
  • Decoupled — can call get_flagged_processes anytime

Cons

  • Two round-trips to Rust on preflight fail
  • Race condition window between scan + fetch
C

Replace details string with JSON payload

Keep details: String in PreflightCheck but serialize structured data as JSON into it for the processes check. Frontend parses it if it looks like JSON, otherwise shows it as text. Backwards-compatible hack.

Pros

  • Zero struct changes

Cons

  • Ugly — stringly-typed data
  • Easy to break
  • Not worth it
